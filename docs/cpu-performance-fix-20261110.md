## 实现

### 流式聚类候选

`trendradar/intelligence/clustering.py` 使用按 domain 划分的标题、token 倒排索引，只保留普通时间窗口内的 postings。CVEs 使用独立历史索引，继续允许跨时间窗口的强关联。Jaccard 阈值为零时同时索引 tag/entity；共享 token 最小值不大于零时回退到窗口内完整候选。

每次只生成当前条目的候选，并保持原先的倒序比较与合并顺序。原 `are_related`、实体冲突、组件时间跨度、CVE 桥接、Story 身份和排名规则保持不变。没有截断候选数量，也没有把批次候选窗口改成“现在减 24 小时”。

审计发现的全量候选图已移除：不再先构造并保存所有条目对。额外内存随窗口内 postings、历史 CVE postings 和单条候选集合增长；最坏密集输入的比较时间仍可能平方增长，不承诺线性时间。

输入至少 1,000 条时，记录输入数量、实际关系比较数、最大单条候选数和比较阶段 CPU 秒。日志不包含标题、正文、消息标识或凭据。

### Scheduler 延迟加载 SDK

仅 `scheduler-once` 使用延迟客户端。入口仍校验配置、维护门禁和 SDK 包是否存在；Bot/Worker 的客户端构造不变。空队列不会导入 Lark SDK。真正发送时初始化一次，继续使用原客户端与超时、API domain 和稳定消息 UUID。

初始化失败返回发送失败，保留冻结批次供现有持久化重试；不创建第二个 Scheduler，不新增循环守护进程，不重写已保存的投递载荷，不重投已登记 Story。

没有新增依赖、配置或 schema 迁移，数据库仍为 v7。表达式索引属于后续可选优化：前次测量收益远小于聚类和启动成本，本次不扩大迁移范围。真正的增量连通分量聚类也不属于本次变更。
